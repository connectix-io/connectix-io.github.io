What is in Connectix

The bot is the product. The softphone, the voice path, the event pipeline, the chat and the reports are how it hears, speaks, looks things up and shows its work. All of it is one Elixir application: one binary on a PC, one container on a server.

Three jobs it is built for

One job first, on one network, measured against the numbers you already keep. These are the three Connectix is built to take.

Tier-1 support

A subscriber calls the support line. The bot answers through mod_earshot and looks up the account by its business line in Fireberry, read-only: the line, the PBX domain, the trunks. What it cannot answer goes to a person, with a summary of what was said and what was found.

NOC questions

The bot answers questions about the switch from the event store: registrations, calls, hang-up causes, agents. It uses fixed reports, and free SQL when the operator turns it on. The alarm that is built is a deadman: it fires when a connected switch goes silent.

Lead and supervisor

Calls, agents and queues; talk time; hourly and daily breakdowns; charts in the chat. The report queries are fixed and written by us, with bound parameters: the model fills in the parameters, not the SQL.

The softphone

A phone on the agent's Windows PC

A small window with a phone page. Connectix runs beside it and bridges the page's audio to your PBX over SIP. One install is one agent.

  • Registers to your PBX with a SIP account saved on the PC. The phone shows Ready only after the PBX has accepted it; a refusal is retried with backoff.
  • Calls in and out, hold and resume, a second line with swap, call waiting, mute, DTMF, blind transfer. A third caller hears busy.
  • No transcoding. Both legs are G.711 A-law; the audio is relayed between WebRTC and RTP inside the application.
  • Signs in by itself. On first start the app offers Load settings file, or a form for the SIP account. A tray icon shows the line status, and a banner says why the line is down and what to check.
  • A Calls tab with the last hundred calls on that PC and redial from the list, and a log view with the last SIP trace and system lines, so a failed registration can be read on the spot.
  • Settings in one file, connectix.toml, private to the user. Export it, import it on a new PC, and that PC is set up. Several SIP accounts; one active.
  • Installer on GitHub Releases, built from a tagged commit, with a checksum file. The installer is not yet code-signed, so Windows shows an unknown-publisher warning.
phone page ── WebRTC audio ──> Connectix ── SIP + RTP (UDP) ──> PBX
The bot on calls

A call answered by the bot, through mod_earshot

FreeSWITCH's mod_earshot streams an answered call's audio to Connectix over a WebSocket and plays back what comes in. The switch owns the audio; Connectix owns the conversation.

  • 16 kHz PCM both ways. The switch does codecs, resampling, voice activity detection, barge-in, DTMF and PCI masking. Connectix hears, thinks and speaks.
  • The caller can interrupt. When the caller starts speaking, queued playback is dropped.
  • Transcripts are kept. What the caller and the bot said is stored with the conversation.
  • The bot can dial out too. An API call has Connectix place a SIP call with the bot on the line instead of a browser. Calls in to the bot come through mod_earshot.
  • Call control is planned. Today mod_earshot streams the audio and Connectix can clear playback; transfer and hang-up from the bot are next. DTMF the caller presses is logged.
  • Speech is Deepgram and Cartesia today: Deepgram for speech to text, Cartesia for text to speech. The language model is configurable: the embedded model gateway or an external one.
  • Authentication is a token set as a channel variable on the switch. Without it, Connectix refuses the handshake.
FreeSWITCH ── mod_earshot ── wss /ws/earshot ──> Connectix (one process per call) │ ▼ speech to text → the bot → text to speech → the caller
WhatsApp

The same bots on WhatsApp Business

Connectix connects to WhatsApp Business messaging. The bots that answer in the chat answer customers' WhatsApp messages too.

  • One bot, more than one channel. A WhatsApp thread is a conversation like any other, with the same tools, approvals and memory.
  • A person can take a thread over and reply to the customer from Connectix.
Events and screen pops

The switch's events, in one pipeline

The events Connectix subscribes to go through one pipeline: it buffers, applies back-pressure, routes them to screen pops, and stores them.

  • Two ways in. Connectix reads the Event Socket directly, or a small agent beside each switch reads it there and sends the frames out over one WebSocket. Both produce the same frames.
  • A YAML rule file decides which event pops which URL for which agent. Pops reach the phone app and the Chrome extension.
  • Subscribed events are stored in a DuckDB file with retention, so the bot and the reports can answer questions about yesterday as well as now. The screen-pop rules can discard events that trigger nothing.
  • A silent switch raises an alarm. A deadman timer notices when a connected switch stops sending; the connection reconnects with backoff.
  • Bounded buffers. Under overload a queue drops the oldest event, counts the drop, and logs once per episode rather than once per message.

The chat

Talk to the bot, approve what it wants to do

The phone app has a CHAT tab. It is where a person asks the bot a question, watches it work, approves or refuses an action, and takes over a conversation.

  • Streamed replies with a Stop button. Conversations, tasks and files in a side rail.
  • Approvals in the chat. When the bot wants to run a tool that changes something, the request appears as a card and waits for a yes.
  • The bot asks back. It can ask the person a question with choices, and carries on with the answer.
  • Take over. A person can take a conversation from the bot; the bot takes no further turns until it is given back. A reply already being written is not cancelled.
  • The bot's memory files are readable. They can be read and edited from the chat, under Files. Skills are code.
  • The same bot in a terminal for an operator, and over an HTTP API with an OpenAPI description. Bots are versioned: draft, publish, retire. Publishing runs a preflight check, two versions can be compared as a diff, and each conversation stays on the version it started with.
Reports

Questions about calls, answered from the store

The default bot answers questions about calls, agents and queues from the softphone's and the switch's records: talk time, answered and missed, hourly and daily breakdowns, with a chart when a chart helps.

  • Fixed SQL with bound parameters. The report queries are written by us and parameterised; the model fills in the parameters, not the query.
  • Free SQL is off by default. It can be turned on per install when an operator wants it.
  • Charts are drawn in the chat as inline SVG from a structured message, so they can be read on the agent's screen without another tool.
Where it runs

On a PC or on your server

Start on one PC with the Windows desktop app. Later, move the same Connectix to a server next to your switch, where operators use the thin Windows client or a browser.

  • The Windows desktop app: the phone and Connectix together on the agent's PC.
  • Connectix Client for Windows: a thin window that connects to a Connectix server.
  • A browser: the same phone page, served by a Connectix server.
  • On a server today: one container (Docker, deployable with Kamal), next to your switch, with its databases on your hardware.
  • Planned, not built yet: a single Linux binary. The same self-contained program as the desktop app, run as a background service, with no Docker needed.
Under the hood

Built on Elixir and Erlang/OTP

Connectix runs on the BEAM, the runtime Ericsson built for telephone switches. Phoenix serves a JSON API and WebSocket channels; the phone page is served from the same origin. The storage is the BEAM's own plus DuckDB. No second runtime.

  • A process per call. Every call, every bot conversation and every connection to the switch is its own lightweight, supervised process. When one fails, that part restarts, not the program.
  • Side by side. Calls and conversations run without blocking each other: the scheduler is preemptive and each process has its own memory.
  • Bounded buffers. Under overload a queue drops the oldest event, counts the drop and logs once, instead of running out of memory.
  • Watched connections. Keepalives, a deadman on a feed that goes silent, and reconnects with backoff from 1 s to 30 s.
  • A live console. The tray's Console… attaches to the running Connectix and looks inside without stopping it, over Erlang distribution, on the same PC only.
  • One self-contained program. The desktop app is a single Elixir release with its runtime inside.
  • Configuration is read at call time, from environment variables on a server or from connectix.toml on a PC. The file is validated before anything is applied.
  • Secrets on a server are named, not written. A YAML file says ${VAR}; the value lives in the environment. On a PC, connectix.toml holds the SIP password and API keys and is readable only by its user.
  • Health and metrics. /health reports per dependency, /health/ready is for a load balancer and is flipped off first on shutdown, /metrics is behind authentication. Optional Uptime Kuma push and InfluxDB log shipping.
  • Storage: Mnesia for accounts, bots and conversations; DuckDB files for events and the model gateway. Both on your hardware.

Where it stands. The softphone, the event pipeline, the voice path, WhatsApp, the chat and the reports are built. An end-to-end suite drives the softphone against a SIPp test PBX; the voice bot is tested with a fake pipeline and an opt-in live test. Call control from the bot is planned.
