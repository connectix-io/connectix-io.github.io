What is in Connectix

The bot is the product. The softphone, the voice path, the event pipeline, the chat and the reports are how it hears, speaks, looks things up and shows its work. All of it is one Elixir application, shipped as one binary.

Three jobs it is built for

One job first, on one network, measured against the numbers you already keep. These are the three Connectix is built to take.

Tier-1 support

A subscriber calls the support line. The bot answers, looks up the subscriber's registration and recent calls on the switch, and fixes what it safely can. Anything else goes to a person, with a summary of what was said and what was found.

NOC watch

The bot reads the switch's events: registrations, failed calls, answer-seizure ratio, trunk errors. It explains a fault in plain words and raises an alert. An action on the switch is fenced and waits for a person's approval.

Lead and supervisor

How many calls today, who answered, who missed, which agent is which extension: fixed reports with bound parameters, so the numbers are the same every time you ask.

The softphone

A phone on the agent's Windows PC

A small window with a phone page. Connectix runs beside it and bridges the page's audio to your PBX over SIP. One install is one agent.

  • Registers to your PBX with a SIP account saved on the PC. The phone shows Ready only after the PBX has accepted it; a refusal is retried with backoff.
  • Calls in and out, hold and resume, a second line with swap, call waiting, mute, DTMF, blind transfer. A third caller hears busy.
  • No transcoding. Both legs are G.711 A-law; the audio is relayed between WebRTC and RTP inside the application.
  • A Calls tab with the last hundred calls on that PC, and a log view with the last SIP trace and system lines, so a failed registration can be read on the spot.
  • Settings in one file, connectix.toml, beside the program or in the data folder. Several SIP accounts; one active.
  • Installer on GitHub Releases, built from a tagged commit, with a checksum file. The installer is not yet code-signed, so Windows shows an unknown-publisher warning.
phone page ── WebRTC audio ──> Connectix ── SIP + RTP (UDP) ──> PBX
The bot on calls

A call answered by the bot, through mod_earshot

FreeSWITCH's mod_earshot streams an answered call's audio to Connectix over a WebSocket and plays back what comes in. The switch owns the audio; Connectix owns the conversation.

  • 16 kHz PCM both ways. The switch does codecs, resampling, voice activity detection, barge-in, DTMF and PCI masking. Connectix hears, thinks and speaks.
  • The caller can interrupt. When the caller starts speaking, queued playback is dropped.
  • The bot can dial out too. An API call has the SIP bridge place a call with the bot on the line instead of a browser.
  • Call control is fenced twice. mod_earshot whitelists the actions it allows (transfer, hang up, play); Connectix asks a person for approval before sending one.
  • The speech and language models are yours to choose. They are configured by key; the application ships with an embedded model gateway and can also point at an external one.
  • Authentication is a token set as a channel variable on the switch. Without it, Connectix refuses the handshake.
FreeSWITCH ── mod_earshot ── wss /ws/earshot ──> Connectix (one process per call) │ ▼ speech to text → the bot → text to speech → the caller
Events and screen pops

The switch's events, in one pipeline

Everything FreeSWITCH reports goes through one pipeline: it buffers, applies back-pressure, routes to the bot and the agents, and stores the event.

  • Two ways in. Connectix reads the Event Socket directly, or a small agent beside each switch reads it there and sends the frames out over one WebSocket. Both produce the same frames.
  • A YAML rule file decides which event pops which URL for which agent. Pops reach the phone app and the Chrome extension.
  • Every event is kept in a DuckDB file with retention, so the bot and the reports can answer questions about yesterday as well as now.
  • A silent switch raises an alarm. A deadman timer notices when a connected switch stops sending; the connection reconnects with backoff.
  • Bounded buffers. Overflow drops the oldest event, counts the drop, and logs once per episode rather than once per message.

The chat

Talk to the bot, approve what it wants to do

The phone app has a CHAT tab. It is where a person asks the bot a question, watches it work, approves or refuses an action, and takes over a conversation.

  • Streamed replies with a Stop button. Conversations, tasks and files in a side rail.
  • Approvals in the chat. When the bot wants to run a tool that changes something, the request appears as a card and waits for a yes.
  • The bot asks back. When it is missing a fact, it asks the person a question instead of guessing.
  • Take over. A person can take a conversation from the bot at any point.
  • The bot's files are readable. Its instructions and skills can be viewed and edited from the chat, so what it does is written down, not hidden.
  • The same bot in a terminal for an operator, and over an HTTP API with an OpenAPI description. Bots are versioned: draft, publish, retire.
Reports

Questions about calls, answered from the store

The default bot answers questions about calls, from the softphone's and the switch's records, with fixed queries and a chart when a chart helps.

  • Fixed SQL with bound parameters. The report queries are written by us and parameterised; the model fills in the parameters, not the query.
  • Free SQL is off by default. It can be turned on per install when an operator wants it.
  • Charts are drawn in the chat as inline SVG from a structured message, so they can be read on the agent's screen without another tool.
Under the hood

One Elixir application

Phoenix serves a JSON API and WebSocket channels; the phone page is served from the same origin. The storage is the BEAM's own plus DuckDB. No second runtime.

  • Supervised processes. Every connection, buffer and cache is a named child of the supervision tree. Recovery is a restart, not an exception handler.
  • Configuration is read at call time, from environment variables on a server or from connectix.toml on a PC. The file is validated before anything is applied; errors never echo values.
  • Secrets are named, not written. A YAML file says ${VAR}; the value lives in the environment. Secrets are compared in constant time.
  • Health and metrics. /health reports per dependency, /health/ready is for a load balancer and is flipped off first on shutdown, /metrics is behind authentication.
  • Logs name the fact and the fix, never a credential, a query string or a body.
  • Storage: Mnesia for accounts, bots and conversations; DuckDB files for events and the model gateway. Both on your hardware.

Where it stands. The softphone, the event pipeline, the voice path, the chat and the reports are built and tested against a test PBX. The bot's first job on a real telecom network is what we are looking for a pilot for.
